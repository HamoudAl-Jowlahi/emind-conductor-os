# المهام

## ✅ ١ — كتالوج الوكلاء + طبقة التثبيت *(2026-08-20)*

**الهدف:** يستعرض المستخدم الوكلاء المتاحين، يقرأ ما يفعل كل واحد ومتطلباته، ويثبّت ما يلزمه. طاقمه = ما اختاره، لا الـ١٩ كلهم.

**لماذا هذه أولاً:** جدول `user_agents` **مطلوب على أي حال** في نظام متعدد المستخدمين — يجب أن تعرف أي وكلاء يملك كل مستخدم. المتجر يعطي هذا الجدول الإلزامي معنىً، ويجعل المهمة ١ب ترث كل شيء منه.

**العمل**
- جدول `user_agents` **بـ `user_id` من الولادة**: `user_id · agent_id · source ('builtin'|'custom') · enabled · config`
- الـ١٩ وكيلاً الحاليون = الكتالوج. **لا نكتب وكيلاً جديداً**
- صفحة الكتالوج: البطاقة تعرض العمل والقسم و**المفاتيح المطلوبة** (من حقل `tools` الموجود أصلاً)
- تثبيت / إلغاء / تعطيل
- `/agents` يعرض **المثبَّت فقط**

**القبول**
- «أ» يثبّت ٣ وكلاء، «ب» يثبّت وكيلين مختلفين — لا تداخل
- البطاقة تقول بصراحة «يحتاج `SLACK_BOT_TOKEN`» قبل التثبيت
- المجدول يشغّل الوكلاء المثبَّتين فقط
- **الوكيل المثبَّت يظهر في كل مكان يظهر فيه الطاقم**: `/agents` · هيكل `/org` · رسم `/brain` · المجدول. الطاقم مصدر واحد، لا أربعة
- **بثّ Conductor ينحصر في المثبَّت.** البثّ إلى وكيل غير مثبَّت يعني محاولة استخدام مفتاح لا يملكه المستخدم — فشل بلا معنى في أحسن الأحوال

**قرار مثبّت:** إضافة وكيل جديد للكتالوج تتم **بالكود** (`real.ts` + `seed.ts` + اختبار + push)، **لا بلوحة إدارة**. قيمة الوكيل هي كوده؛ ولوحة تأليف لن تنتج إلا وكيل تعليمات نصية — وهو ما تفعله المهمة ١ب أصلاً. وبالكود تحصل على مراجعة واختبارات وتراجع.

**تسمية دقيقة:** هذا **كتالوج** لا متجر. إضافات VS Code يكتبها طرف ثالث؛ هنا نكتبها نحن. فتحه لمؤلفين خارجيين مشروع منفصل (عزل · مراجعة · ثقة) — **ليس امتداداً بسيطاً**.

**الجهد:** ٣ أيام · **يعتمد على:** لا شيء

## ⬜ ١ب — الوكلاء الديناميكيون

**الهدف:** ينشئ المستخدم وكيلاً من نموذج في `/agents`: اسم + وصف عمله + جدول. يركب على نفس جدول المهمة ١ بـ `source: 'custom'`.

**العمل**
- نموذج الإنشاء + `POST /api/agents/custom`
- **النموذج يسأل عن الركيزة** (مبيعات · تسويق · تقنية · مالية · اتصالات · عملاء) — وإلا طفا الوكيل في `/org` بلا انتماء
- `lib/agents/custom.ts` — الوصف يصير `system prompt`، ويشغّله Gemini
- تعديل اختبار التطابق 1:1 ليقبل الوكلاء المخصّصين

**القبول**
- أنشئ وكيلاً → يظهر في الطاقم → شغّله → رد حقيقي
- **يظهر تحت ركيزته في `/org` وكعقدة في `/brain`** — تماماً كالوكلاء المدمجين
- جدوله `*/5 * * * *` → يعمل وحده
- وكيل «أ» لا يظهر لـ«ب»

**صريح:** الوكيل المخصّص **يقرأ ويحلل ويبلّغ. لا ينفّذ أفعالاً خارجية** — ذلك في المهمة ٩. الوصف النصي لا يمنح أدوات؛ الأدوات تُكتب بالكود.

**الجهد:** يوم واحد (كان ٣ — يرث طبقة التثبيت) · **يعتمد على:** ١

## 🟨 ٢ — عزل البيانات: `user_id` على الجداول الـ٣٠ *(جارية)*

**الهدف:** أساس تعدد المستخدمين. بدونه يرى كل مستخدم بيانات الجميع.

**العمل**
- ترحيل يضيف `user_id` لكل جدول يحمل بيانات مستخدم (الوكلاء، التشغيلات، الرسائل، القمع، المالية، الاجتماعي، المهام…)
- **فرض العزل في طبقة المستودعات** — لا في الصفحات. `getDb()` يصير مربوطاً بالمستخدم الحالي
- كل صفوف اليوم تُنسب لأول مستخدم (المالك)
- اختبار يفرض: **لا استعلام يعبر حدود المستخدم**

**القبول**
- مستخدمان، بيانات مختلفة تماماً، صفر تسريب
- اختبار يفشل عمداً لو نسي مطوّر شرط `user_id`

### التقدّم (2026-08-20)

| ✅ منجز | التفصيل |
|---|---|
| تصنيف الجداول | `lib/tenancy.ts` — ٧ مشتركة · ٤ هوية · **٢٠ مملوكة**، واختبار يسقط لو أُضيف جدول بلا تصنيف |
| الترحيل | `user_id` **+ فهرس** على الجداول العشرين، بـ`ALTER` فيرقّي القواعد القائمة في مكانها |
| مسار الترقية | `claimOrphanRows()` يمنح صفوف ما قبل تعدد المستخدمين لأول مستخدم، ولا يمنح الثاني شيئاً |

| ⬜ المتبقي | الحجم المقيس |
|---|---|
| تقييد الاستعلامات | **٥٨ عبارة مُعدّة** عبر ٢٠ جدولاً |
| فصل `openDb` إلى اتصال + مصنع مستودعات بنطاق | مقياس بسيط، جُرّب ونجح، أُجّل ليأتي مع التقييد |
| ربط الصفحات والمسارات بالمقبض المقيَّد | ١٣ نقطة قراءة |
| اختبار التسريب بين مستخدمين | بعد التقييد |

**ملاحظة صريحة:** المحاولة الأولى للتقييد كتبت المعامل بصيغة مُسمّاة (`@__uid`) بينما الاستعلامات تستخدم المواضع (`?`) — و`better-sqlite3` لا يقبل مزجهما. تراجعت عنها بدل شحن عزل نصف صحيح. الحل: تحويل الـ٥٨ عبارة إلى معاملات مُسمّاة، أو ضبط ترتيب المواضع لكل عبارة على حدة.

**الجهد:** ١٠–١٤ يوماً · **يعتمد على:** ١ · **أثقل مهمة في الملف**

## ⬜ ٣ — مخزن مفاتيح مشفّر لكل مستخدم

**الهدف:** يضع كل مستخدم مفاتيحه، مشفّرة، معزولة. **يحلّ محل `.env.local` المشترك** الذي يمسح فيه مفتاح مستخدم مفتاح الآخر.

**العمل**
- جدول `user_credentials` (`user_id`, `key_name`, `ciphertext`, `iv`)
- تشفير AES-256-GCM بمفتاح جذر من البيئة (`node:crypto`، بلا حزم جديدة)
- إعادة كتابة `lib/creds.ts`: يقرأ اليوم من ملف عند الإقلاع → يقرأ مفاتيح **المستخدم الحالي** في كل طلب
- `/integrations` يكتب إلى المخزن بدل الملف — **الواجهة موجودة، المخزن فقط يتغير**

**القبول**
- «أ» و«ب» لهما مفتاح Stripe مختلف، وكل وكيل يستخدم مفتاح صاحبه
- لا مفتاح خام في قاعدة البيانات (تحقق مباشر بالاستعلام)
- لا مفتاح يُعاد إلى الواجهة أبداً — `set` / `not set` فقط

**الجهد:** ٣ أيام · **يعتمد على:** ٢

## ⬜ ٤ب — الدخول بحساب Google

**الهدف:** «سجّل الدخول بـ Google» بجانب البريد وكلمة المرور. مدخلان، وجلسة واحدة.

**لماذا قبل النشر:** يقلّص المهمة ٥ لا يضيف إليها — لا كلمة مرور تُنسى أو تُسرَّب، والبريد يصل **موثّقاً**، و**Google يتولى التحقق بخطوتين** نيابةً عنك.

**العمل**
- `GET /api/auth/google` → إعادة توجيه مع `state` موقّع (حماية CSRF)
- `GET /api/auth/google/callback` → تبادل الرمز → قراءة الاسم والبريد → إيجاد المستخدم أو إنشاؤه → **`createSession` نفسها**
- عمود `google_sub` على `users` للربط الثابت
- زر في `LoginForm`

**بلا حزمة جديدة.** نحتاج **الهوية فقط لا الوصول إلى خدمات Google** — فلا تجديد رموز ولا حفظها ولا PKCE. وAuth.js كان سيطالب بامتلاك طبقة الجلسات المبنية والمختبرة، فنستبدل ما يعمل بما هو أثقل، مقابل مزايا لا نحتاجها.

**قرار الربط:** بريد واحد = حساب واحد بمدخلين. **الشرط الأمني:** الربط فقط إن أعاد Google `email_verified: true` — وإلا استطاع مهاجم أن يسجّل ببريد الضحية قبلها فيرث حسابه دخولها.

**القبول**
- دخول بـ Google لمستخدم جديد → حساب + جلسة
- نفس البريد الذي سجّل بكلمة مرور → **نفس الحساب**، لا ثانٍ
- بريد غير موثّق من Google → رفض الربط
- `state` مفقود أو غير مطابق → رفض الطلب

**يحتاج منك:** مشروع Google Cloud ← شاشة موافقة ← `OAuth 2.0 Client ID` (Web application) ← `GOOGLE_CLIENT_ID` و`GOOGLE_CLIENT_SECRET`. رابط الإرجاع: `/api/auth/google/callback` (نسخة للتطوير وأخرى للنطاق الحقيقي).

**الجهد:** يوم · **يعتمد على:** ٢

## ⬜ ١٣ — لوحة قياس للمالك (Admin)

**الهدف:** **قياس لا إنشاء.** لوحة تراها أنت وحدك: من يستخدم النظام، وأي وكيل ينجح وأيّها يفشل.

**لماذا بعد النشر:** لا معنى لقياس بلا مستخدمين. وقبل ذلك الأرقام صفر.

**ما تعرضه**

| المحور | المقياس |
|---|---|
| النمو | تسجيلات جديدة · مستخدمون نشطون (٧ و٣٠ يوماً) · معدل البقاء |
| الوكلاء | **كم مستخدماً ثبّت كل وكيل** · ترتيب الأكثر تثبيتاً · الأكثر إلغاءً |
| الجودة | **نسبة نجاح تشغيلات كل وكيل** · الأكثر فشلاً · أسباب الفشل المتكررة |
| الاتصالات | أي مفاتيح يوصّلها الناس فعلاً · أيّها يتجاهلونه |
| التكلفة | استهلاك النموذج اللغوي لكل مستخدم (يعتمد على المهمة ١٠) |

**الخبر الجيد:** أهم البيانات **موجودة أصلاً**. جدول `agent_runs` يسجّل كل تشغيل بحقل `ok` وملخّص السبب منذ اليوم الأول — نسبة النجاح وأسباب الفشل استعلام واحد، لا بناء جديد.

**العمل**
- حقل `role` على المستخدم (`owner` / `user`) + حارس يمنع غير المالك — **لا توجد أدوار اليوم**
- `/admin` محمية بذلك الحارس
- استعلامات تجميع + رسوم بلغة المشروع البصرية
- **بلا بيانات شخصية**: أرقام مجمّعة، لا محتوى رسائل ولا مفاتيح ولا بيانات عملاء المستخدمين

**القبول**
- مستخدم عادي يفتح `/admin` → ٤٠٣ لا صفحة فارغة
- نسبة نجاح كل وكيل تطابق `agent_runs` يدوياً
- لا حقل يعرض محتوى بيانات أي مستخدم

**الجهد:** ٣ أيام · **يعتمد على:** ٧ (النشر) · ١٠ لعمود التكلفة
